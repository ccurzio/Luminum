# Luminum Wire Protocol Specification

**Version:** 1.0-draft
**Status:** PROPOSED — v1.0-draft. Core transport decisions locked: Ed25519 (Crypt::Perl::Ed25519), Mosquitto, MQTT 3.1.1, TLS-bound signing certificate, data ports 10465 + 10704, JSON everywhere.
**Scope:** All client↔server communication for Luminum Server and Luminum Clients (all platforms), including Lumy module traffic.

This document supersedes the ad-hoc message exchange currently implemented in `client/linux/src/main.rs` (MessagePack over raw TCP) and `server/broker.pl` (JSON envelope over raw TCP). Both ends must conform to this specification. Where this document makes a choice that is not yet settled, it is marked **[DECISION]**.

---

## 1. Goals

1. **One envelope, one signature scheme, every channel.** The same message format is used over MQTT and over direct-connect. No channel-specific encodings.
2. **MQTT is the control plane.** All commands, responses, check-ins, and events flow over MQTT.
3. **Direct-connect is the bootstrap and data plane.** It is used only for (a) first-time registration (where MQTT credentials do not yet exist) and (b) bulk transfers (package delivery, oversized sensor output).
4. **Every message is authenticated and integrity-protected** by per-message signature, independent of transport encryption. A compromised transport must not allow message forgery.
5. **Mosquitto is the broker.** The server-side MQTT broker is Mosquitto, running as its own service. The Luminum broker process (`broker.pl`) is the application layer: it authenticates clients (Mosquitto auth hook → DB check of the secret hash), subscribes to all `luminum/{SID}/#` traffic, processes messages, and publishes commands. The exact Mosquitto auth and ACL mechanisms are confirmed against the deployed version (§4.1, §4.3).

Non-goals: user-facing web console traffic (nginx/PHP), inter-endpoint communication.

---

## 2. Transport Channels

| Channel | Protocol | Port (default) | Purpose |
|---|---|---|---|
| Control | MQTT over TLS 1.2+ | 8883 (`MPORT`) | Commands, responses, check-ins, events, LWT |
| Bootstrap/Data (server) | TLS 1.2+ over TCP, length-prefixed frames | 10465 (`LPORT`) | Registration, client→server bulk data |
| Data (client inbound) | TLS 1.2+ over TCP, length-prefixed frames | 10704 (`IPORT`) | Server→client bulk data (package delivery) |
| Local IPC (client-side only) | TCP, length-prefixed frames | 10461 (`LPORT_LOCAL`) | Lumy ↔ client process communication on the endpoint |

- The MQTT port is the standard mqtts port to simplify firewalling; it is configurable via the `MPORT` server config key.
- **10465 (`LPORT`)** is the server's listener. The client connects out to `server:10465` for registration and for client→server bulk data (oversized sensor results).
- **10704 (`IPORT`)** is the client's inbound listener. The server connects to `client:10704` for server→client bulk data (package delivery). The MQTT `deploy` command carries the data reference; the server then opens a TLS connection to the client's 10704 to push the package. The client must be reachable on this port (NAT/firewall rules are the operator's responsibility).
- All TLS channels: TLS 1.2 minimum, TLS 1.3 preferred. Certificate verification is mandatory on both ends; no fallback to plaintext on any channel.

## 3. Security Model

### 3.1 Keys

| Key | Generated by | Stored by | Purpose |
|---|---|---|---|
| Server TLS certificate + private key | Server (setup) | Server; cert distributed to clients at registration | Transport encryption, server identity |
| Server signing keypair (Ed25519) | Server (setup) | Private: server only. Public: carried in the server signing certificate (§7.1) | Signing server→client messages |
| Client signing keypair (Ed25519) | Client, at first run | Private: client config DB (file mode 0600). Public: sent at registration, stored server-side in `CLIENTS.AUTH.PUBKEY` | Signing client→server messages |
| Client fingerprint | Client, at first run | Client config DB; server `CLIENTS.AUTH.FINGERPRINT` | Client identity binding |
| Client MQTT secret | Server, at registration | Client config DB (0600); server stores SHA-256 hash only | MQTT broker authentication |

- **Fingerprint** = lowercase hex SHA-256 of the client's public key in SPKI/DER encoding. This matches the existing `FINGERPRINT` column and the hex validation already present in `iafis()`.
- The fingerprint is the client's stable identity. If the client's keypair is regenerated (reinstall, key loss), the fingerprint changes and the client must re-register; the old record is deactivated, not silently replaced.

### 3.2 Registration (credential bootstrap)

Registration is the only flow that uses the bootstrap channel to *create* credentials. It is specified in §7.1. Summary:

1. Client proves possession of the server key (`SKEY`, provisioned out-of-band by the administrator at install time).
2. Client presents its hostname, OS info, public key, and fingerprint.
3. Server validates `SKEY`, stores the public key + fingerprint, assigns a numeric UID, and issues the MQTT client secret — over the same TLS connection.
4. From that point on, the client authenticates to the MQTT broker with `username = UID`, `password = client secret`.

### 3.3 Per-message authentication

Every protocol message (both directions, both channels) carries a signature:

- `sig` = signature over the **canonical JSON** (§5.3) of the envelope **with the `sig` field removed**.
- Client→server: signed with the client's private key; server verifies against the stored `PUBKEY` for the claimed UID.
- Server→client: signed with the server's private key; client verifies against the server public key received at registration.
- Verification failure ⇒ message dropped, connection flagged, event logged (`MSG_AUTH_FAIL`). Three failures on one connection ⇒ connection terminated.

Transport encryption (TLS) provides confidentiality; the signature provides authenticity and integrity. Both are required.

### 3.4 Signature algorithm

**Ed25519 (confirmed).** Reasons: no padding modes to get wrong, small keys/signatures, fast on endpoint hardware, first-class support in the Rust ecosystem (e.g. the `ed25519-dalek` crate).

**Perl implementation: `Crypt::Perl::Ed25519` (confirmed, installed and verified).** Part of the `Crypt::Perl` distribution (v0.38). Pure-Perl Ed25519 — no OpenSSL dependency. API:

```perl
use Crypt::Perl::Ed25519::PrivateKey;
use Crypt::Perl::Ed25519::PublicKey;

# Generate (or import from 32-byte seed)
my $priv = Crypt::Perl::Ed25519::PrivateKey->new();          # random
my $priv = Crypt::Perl::Ed25519::PrivateKey->new($seed32);   # deterministic

# Sign (returns 64-byte octet string)
my $sig = $priv->sign($message);

# Verify (on public key object)
my $pub  = $priv->get_public_key();
my $ok   = $pub->verify($message, $sig);   # true / false

# Raw 32-byte public key (for fingerprint / storage)
my $pub_bytes = $pub->get_public();

# DER / PEM export
my $der = $priv->to_der();
my $pem = $priv->to_pem();
```

Key storage: the 32-byte raw seed (`get_private()`) and 32-byte raw public key (`get_public()`) are what go in the config DB. DER/PEM are available for certificate generation. Signatures are 64 bytes, base64-encoded in the `sig` field.

**Rust implementation: `ed25519-dalek`** (or equivalent). The two implementations MUST produce identical signatures for the same key + message — this is enforced by the shared test vector (§5.3).

## 4. MQTT Design

### 4.1 Connection parameters (client)

| Parameter | Value |
|---|---|
| Protocol version | MQTT 3.1.1 |
| Client ID | The client's UID (string form) |
| Clean session | `false` (persistent session so QoS 1 commands queue while offline) |
| Keep alive | 60 seconds |
| Will (LWT) | Topic `luminum/{SID}/{UID}/status`, QoS 1, retained, payload = a valid signed envelope with `status: "offline"` (see §7.5) |
| Auth | Username = UID, password = client secret; one-way TLS with server certificate verification |

**Authentication — Mosquitto built-in `password_file`.** Mosquitto performs the MQTT login check against a `password_file` (salted PBKDF2-SHA512 hashes, maintained with `mosquitto_passwd`). The broker process keeps this file in sync with `CLIENTS.AUTH`: it adds the entry when a client registers and removes it when a client is deactivated, then signals Mosquitto to reload (`SIGHUP`). A deactivated UID is therefore rejected at login because its entry no longer exists. No C plugin or external auth callback is required.

Because MQTT 3.1.1 has no Message Expiry Interval, a command queued in a persistent session while the client is offline does not expire automatically. Stale-command protection is provided instead by the server-side command timeout (§9.3) and client-side deduplication (§9.2): the server tracks outstanding commands and abandons them past the deadline, and the client ignores any command whose `id` it has already processed.

### 4.2 Topic scheme

Per-endpoint topics (the `{UID}` target):

```
luminum/{SID}/{UID}/cmd      server → client   commands (query, deploy, config)
luminum/{SID}/{UID}/resp     client → server   responses to commands
luminum/{SID}/{UID}/status   client → server   check-ins + LWT (retained)
luminum/{SID}/{UID}/events   client → server   unsolicited events (e.g., Integrity alerts)
```

Group topics (fan-out to a set of endpoints; `cmd` only, server → client):

```
luminum/{SID}/all/cmd            all endpoints
luminum/{SID}/os/{os}/cmd        all endpoints of OS {os} (e.g. os/linux)
luminum/{SID}/grp/{name}/cmd     all endpoints in custom group {name}
```

- `{SID}` is the Luminum Server ID; `{UID}` is the numeric client ID. All lowercase, no wildcards in granted topics except as listed in §4.3. `{UID}` is numeric, so the group targets `all`/`os`/`grp` never collide with a real endpoint.
- **Lumy routing is in the envelope, not the topic.** The `lumy` field (§5.1) selects the handling module. This keeps the ACL surface small and lets a single subscription carry all module traffic.
- A client subscribes to its own `cmd` topic plus the group `cmd` topics it belongs to: `all`, its OS (`os/{osplat}`), and each custom group in `INGROUPS` (delivered to the client via a `setgroups` command). Group topics carry commands only; responses, check-ins, and events always go to the per-UID topics.
- Commands are **never retained**. Status is **retained** (last known state). Resp and events are never retained.
- The server publishes nothing to `status`/`resp`/`events`; clients publish nothing to `cmd`. Enforced by ACL (§4.3).

### 4.3 Access control

Per-client ACL (client authenticated as UID `{UID}`):

| Direction | Topic |
|---|---|
| subscribe | `luminum/{SID}/{UID}/cmd` |
| subscribe | `luminum/{SID}/all/cmd` |
| subscribe | `luminum/{SID}/os/{os}/cmd` (its own OS) |
| subscribe | `luminum/{SID}/grp/{name}/cmd` (its groups) |
| publish | `luminum/{SID}/{UID}/resp` |
| publish | `luminum/{SID}/{UID}/status` |
| publish | `luminum/{SID}/{UID}/events` |

Server ACL: unrestricted within `luminum/{SID}/#`.

No client may read or write another client's **per-UID** topics. ACLs are enforced by Mosquitto via **static `pattern` rules in an `acl_file`**, keyed on the client's UID (used as the MQTT username, §4.1) through the `%u` substitution:

```
# Per-endpoint topics: each client reads its own cmd, writes its own resp/status/events
pattern read  luminum/{SID}/%u/cmd
pattern write luminum/{SID}/%u/resp
pattern write luminum/{SID}/%u/status
pattern write luminum/{SID}/%u/events

# Group topics: readable by any authenticated client. 'pattern' rules cannot use
# +/# wildcards (only %u/%c/%a substitution), so the OS and group topics are
# enumerated explicitly — one line per known OS value and per group name. The
# server regenerates these lines (and SIGHUPs the broker) when groups change.
pattern read  luminum/{SID}/all/cmd
pattern read  luminum/{SID}/os/linux/cmd
pattern read  luminum/{SID}/os/windows/cmd
pattern read  luminum/{SID}/os/macos/cmd
pattern read  luminum/{SID}/grp/{name}/cmd

# Server: unrestricted within the Luminum tree. The server only PUBLISHES (and
# reads back resp/status/events), so a 'topic' rule is sufficient here.
user {server-uid}
topic readwrite luminum/{SID}/#
```

> **Mosquitto 2.0.x `topic` vs `pattern` delivery quirk.** A `topic [read|write]` ACL grants the SUBSCRIBE (a SUBACK is sent, no denial) but **never delivers the message** to the subscriber; only `pattern` ACLs actually deliver. This was confirmed empirically against Mosquitto 2.0.21. It is why the per-UID and group *read* grants above all use `pattern`. The quirk does not affect the *publisher* path, which is why the server's `topic readwrite luminum/{SID}/#` still lets it publish to every topic. The same quirk is why `pattern` (the only delivering form) must enumerate the variable OS/group topics instead of using `os/#`/`grp/#`.

Group topics are readable by any authenticated client because Mosquitto's static `pattern` rules can only substitute the username (`%u`), not a per-client attribute such as OS — so they cannot express "Linux clients may read only `os/linux`". Isolation therefore comes from the **client subscribing only to the group topics it belongs to** (§4.2): a Linux client subscribes to `os/linux/cmd`, not `os/windows/cmd`. This is safe because commands are server-signed (a client cannot forge or escalate them) and the hard write boundary is per-UID (a client can only publish to its own `resp`/`status`/`events`); a command delivered to the wrong OS is simply ignored by that client. Tighter isolation would require a dynamic ACL (Mosquitto C/security plugin), which is ruled out by the no-build-in-production constraint.

The server-side worker authenticates under a dedicated username (not a client UID) and is granted unrestricted access to `luminum/{SID}/#` via the `user` rule above. Because the client rules are static patterns rather than per-client entries, the ACL file does not grow with the client count and requires no dynamic callback or plugin.

### 4.4 QoS and delivery semantics

| Traffic | QoS | Notes |
|---|---|---|
| `cmd` | 1 | At-least-once ⇒ clients must deduplicate (§9.2). Server tracks outstanding commands and times them out (§9.3). |
| `resp` | 1 | Correlated to `cmd` by message `id`. |
| `status` (check-in) | 0 | Loss of a single check-in is harmless; the next one arrives in `CHECKININT`. |
| `status` (LWT) | 1, retained | Must be delivered. |
| `events` | 1 | Security-relevant; must not be silently lost. |

Broker maximum packet size: **64 KiB** payload. Messages larger than this must not be published; use the data channel reference pattern (§8.3).

## 5. Message Envelope

### 5.1 Fields

All messages, both directions, both channels:

| Field | Type | Req | Description |
|---|---|---|---|
| `v` | string | yes | Protocol version, `"1.0"`. Major mismatch ⇒ reject. |
| `id` | string (UUIDv4) | yes | Unique message ID. Used for correlation and deduplication. |
| `ts` | integer | yes | Unix epoch seconds, sender's clock. Server is authoritative for scheduling. |
| `src` | string | yes | `"client"`, `"server"`, or `"lumy"` (local IPC only, §8.2). |
| `uid` | string | yes | Numeric UID (string form). `"0"` only in registration requests. |
| `lumy` | string | yes | Module name, lowercase: `"core"` or a Lumy name (`"integrity"`, …). |
| `action` | string | yes | Action name within the Lumy (§6). |
| `status` | string | yes | `"OK"`, `"ERR"`, or a Lumy-defined status. |
| `err` | string | no | Human-readable error detail; present when `status` is `"ERR"`. |
| `data` | object | no | Action-specific payload (§6). Always an object, never an array. |
| `sig` | string (base64) | yes | Signature per §3.3. |

### 5.2 Example

Client check-in:

```json
{
  "v": "1.0",
  "id": "3f6c1d2e-8a4b-4e5f-9c6d-1a2b3c4d5e6f",
  "ts": 1735689600,
  "src": "client",
  "uid": "451",
  "lumy": "core",
  "action": "checkin",
  "status": "OK",
  "data": {
    "hostname": "tango",
    "osplat": "Linux",
    "osrel": "Debian 12.10",
    "clientver": "0.0.1",
    "ipv4": "172.16.0.10"
  },
  "sig": "MEUCIQ..."
}
```

### 5.3 Canonicalization (for signing)

The signature is computed over the canonical JSON encoding of the envelope with `sig` removed:

1. Object keys sorted lexicographically (byte order).
2. No whitespace between tokens.
3. Strings UTF-8; escaping per RFC 8259 (only `"` `\` and control characters escaped; no Unicode escaping of non-ASCII).
4. Numbers rendered in minimal decimal form (no trailing `.0`, no exponents for in-range integers).
5. `null`, `true`, `false` per RFC 8259.

Both implementations MUST include a shared test vector (a fixed envelope with its expected canonical form and signature under a fixed test key) in the test suite. **Done:** the vector is at `tests/testvector.json` (fixed seed `0x00..0x1f`); the Rust check is `client/linux/tests/testvector.rs` (`cargo test`) and the Perl check is `client/linux/tests/verify_vector.pl`. Regenerate with `cargo run --example gentestvector` from `client/linux`.

### 5.4 Encoding on the wire

- MQTT: payload is the UTF-8 JSON serialization of the envelope (pretty or compact — irrelevant; the signature covers the canonical form, not the wire form).
- Direct-connect / local IPC: same JSON, inside a length-prefixed frame (§8.2).

**JSON everywhere (confirmed).** The current Rust client uses MessagePack and the current broker expects JSON; this spec picks one. JSON is chosen for debuggability on the wire (critical for a security product being rolled out into real environments) and because both Perl (`JSON::PP`, core) and Rust (`serde_json`, already a dependency) handle it natively. MessagePack is dropped from the protocol. If payload size ever becomes a real constraint, that is a v2 change with version negotiation.

## 6. Message Catalog

### 6.1 Core (always present)

| Direction | lumy | action | `data` fields | Description |
|---|---|---|---|---|
| c→s (bootstrap) | core | `register` | `hostname`, `fingerprint`, `pubkey` (base64 SPKI/DER), `osplat`, `osrel`, `clientver`, `ipv4`, `ipv6` (opt), `serverkey` | First-time registration. Only valid with `uid` = `"0"`. |
| s→c (bootstrap) | core | `register` | `uid`, `sid`, `mqtthost`, `mqttport`, `mqttsecret`, `serverpubkey` (base64 SPKI/DER) | Registration response. Only valid over the bootstrap channel. `sid` is the Luminum Server ID used to build MQTT topics (§4.2). |
| c→s | core | `checkin` | `hostname`, `osplat`, `osrel`, `clientver`, `ipv4` (opt), `ipv6` (opt), `checkin_secs` (the client's current interval, seconds) | Periodic liveness + state refresh. Interval = `CHECKININT`; the reported `checkin_secs` lets the server detect drift and push a correction (§7.2). |
| c→s | core | `unregister` | — | Client-initiated deactivation request (sanctioned uninstall flow). |
| s→c | core | `query` | `qid`, `sensors` (array of `{sid, params}`) | Run named sensors, return results. Definitions arrive via `config` (§7.3). |
| c→s | core | `answer` | `qid`, `results` (array of `{sid, output}` on success or `{sid, err}` on per-sensor failure) or `ref` (§8.3) | Response to `query`. `status` is `OK` (all succeeded), `PARTIAL` (some failed), or `ERR` (malformed/none succeeded). Correlated by `qid` inside `data`; message `id` still unique per message. |
| s→c | core | `deploy` | `aid`, `pkgid`, `ref` (§8.3), `profile` (opt) | Deploy a package. |
| c→s | core | `report` | `event` (string), `detail` (object) | Unsolicited client report (e.g., deploy completion, local error). |
| s→c | core | `config` | Lumy-specific key/value set; for `lumy` = `core`, `data.sensors` (array of sensor definitions: `sid`, `name`, and the per-OS script type/script fields) | Push configuration to a Lumy (replaces the current IPC `newconfig`/`setconfig` round-trip as the server-side source of truth). Core sensor definitions are upserted by the client into its local sensor table (§7.3). |
| s→c | core | `setgroups` | `groups` (array of names; the full replacement list, may be empty) | Update the endpoint's group membership (§4.2): the client re-subscribes its group `cmd` topics, persists the list, and responds `OK`; a name outside `[A-Za-z0-9_.-]` is rejected as a whole with `err: "INVALID_DATA"`. |
| s→c | core | `setcheckinint` | `checkin_secs` (the directed interval, seconds) | Direct the endpoint's check-in interval (§7.2): the client persists it (`CHECKIN_SECS`) and applies it to its check-in cadence, and responds `OK`; a value outside 1–86400 seconds is rejected with `err: "INVALID_DATA"`. |

### 6.2 Lumy-defined actions

Each Lumy namespace owns its action names. The core broker validates `lumy`/`action` syntax and routing only; semantics are the Lumy's. Conventions:

- Action names: lowercase alphanumeric, e.g. `integrity/setconfig`, `integrity/alert`.
- Client→server alerts (e.g., Integrity filesystem changes) use the `events` topic with `lumy` set to the module name.
- A Lumy MUST NOT define an action named `register`, `checkin`, or `unregister`.

### 6.3 Versioning and unknown actions

- Receiver gets an unknown `action` for a known `lumy`: respond `status: "ERR"`, `err: "UNKNOWN_ACTION"` (for `cmd` traffic; events are dropped and logged).
- Receiver gets an unknown `lumy`: same, `err: "UNKNOWN_LUMY"`.
- Major version mismatch (`v`): drop, log `PROTO_VERSION_MISMATCH`, no response.

## 7. Flows

### 7.1 Registration (bootstrap channel)

```
Client                              Server
  |--- TLS connect (LPORT) ---------->|
  |--- frame: register (uid=0) ------->|   SKEY check, pubkey+fingerprint stored,
  |<-- frame: register (uid=N) -------|   UID assigned, secret generated
  |--- TLS close ---------------------->|
  |=== MQTT connect (MPORT, uid/secret) =>|
  |=== publish status (retained) ----->|
```

- The `register` request is signed with the client's new key (the server cannot verify it against a stored key yet — it *extracts* the pubkey from the message and verifies the signature against it; this is the possession proof).
- The `register` response is signed with the server's Ed25519 key. **Bootstrap trust anchor (TLS-bound signing certificate, confirmed):** the server holds a dedicated Ed25519 signing certificate issued by the same CA that issues the server TLS certificate. The client validates this signing certificate against its trusted CA — the same trust root it already uses for the TLS handshake — extracts the Ed25519 public key, and uses it to verify all server→client signatures. The `serverpubkey` field in the register response is retained as a convenience and is cross-checked against the key in the validated signing certificate; a mismatch is a fatal error. Setup must therefore generate the Ed25519 signing keypair and signing certificate and distribute the CA (or the signing certificate) to clients — this extends the existing Certificate/Key Setup work.
- The MQTT secret is transmitted only inside the signed, TLS-protected bootstrap response. The server stores only its SHA-256 hash.
- Re-registration with an existing fingerprint is rejected (`status: "ERR"`, `err: "ALREADY_REGISTERED"`).

### 7.2 Check-in

- Client publishes to `status` (QoS 0, retained) every `CHECKININT` minutes.
- Server updates `CLIENTS.STATUS` (hostname, IPs, OS, clientver, `LASTSEEN`, `CSTATE`).
- **Check-in interval sync.** The client reports the interval it is currently using (`checkin_secs`, seconds) in every check-in. The server compares it with `CHECKININT` (minutes, read live from `SYSTEM.CONFIG`); on a mismatch it publishes a signed `core/setcheckinint` on the client's `cmd` topic, and the client persists the value (`CHECKIN_SECS`) and applies it from the next check-in. Because the comparison happens on every check-in, a freshly-installed client converges on its first check-in, an admin change to `CHECKININT` propagates to every client on its next check-in without a broker restart, and a lost push self-heals on the following check-in.
- A check-in from a UID whose fingerprint no longer matches the stored `PUBKEY`-derived fingerprint ⇒ `CSTATE = "CRIT"`, log `FINGERPRINT_MISMATCH`, and reject further messages from that connection. (Replaces `iafis()`'s role; `iafis()` becomes a lookup, not a per-message re-hash.)

### 7.3 Query / answer

```
Server                          Client
  |-- publish cmd: config (QoS1) ->|  (sensor definitions, when the client
  |-- publish cmd: query (QoS1) ->|    does not already have them)
  |                               | execute sensors
  |<-- publish resp: answer ------|   (same data.qid)
```

- **Sensor definitions.** A `query` names sensors by `sid` only, so the client must already hold their definitions (script + type, from the server's sensor store). The console delivers them per query: it enqueues a `core/config` command carrying `data.sensors` for exactly the sensors in the query immediately before the `core/query` (same outbox, lower row ID). Outbox publish order (ID ascending), QoS 1 to the same topic, and the client's sequential processing guarantee the definitions reach the client first. The client upserts them into a local sensor table (`SID`, name, script type, script) and answers the query.
- **Parameter injection.** `params` values are resolved server-side (provided values merged with the sensor's declared defaults) and carried in the `query`; the client substitutes each value at the `${name}` points in the sensor script before execution.
- **Per-sensor results.** Each `results` entry is `{sid, output}` on success or `{sid, err}` on failure (e.g. `UNKNOWN_SENSOR`, `EXEC_ERROR`, `TIMEOUT`); the answer `status` is `OK` / `PARTIAL` / `ERR` (§6.1). A single sensor cap (30 s) bounds one script; the server's command deadline (`CMDTIMEOUT`) bounds the whole query.
- **Deadlines.** The server tracks outstanding `query` commands with a deadline. No `answer` by deadline ⇒ command marked `TIMEDOUT`; v1 does not republish a timed-out query (a redelivered query would be deduplicated client-side and never re-answered) — the console re-enqueues it if it wants a retry. Other commands are republished past their deadline per the action policy (§9.1).
- **Size.** Small results ride MQTT. An answer that would exceed the broker's maximum packet size is answered `ERR` with `err: "OUTPUT_TOO_LARGE"`; oversized results travel via the data channel reference pattern (§8.3).
- Client deduplicates by message `id` (§9.2) — a redelivered `query` after a partial MQTT outage must not double-execute sensors with side effects. Sensors must be written idempotently; the spec cannot guarantee it.

### 7.4 Deploy

Same shape as query/answer with `deploy`/`report`. Package bytes travel via the data channel reference pattern (§8.3); the `deploy` command carries only the reference and metadata.

### 7.5 Offline detection (LWT)

- The client's will message is a **pre-signed** `status: "offline"` envelope, retained, on the `status` topic.
- On abnormal disconnect the MQTT broker publishes the will ⇒ server marks the client offline immediately (UI `CSTATE` update, `LASTSEEN` preserved).
- `MISSINGAFTER` (days) still governs the *missing* classification; LWT only provides promptness.
- The client MUST update (re-set) its will on every reconnect. A retained `offline` status from a stale will is corrected by the first post-connect check-in (retained overwrite).

## 8. Direct-Connect Channel (Bootstrap/Data)

### 8.1 Usage

Exactly two purposes: registration (§7.1) and bulk data transfer (§8.3). No other traffic. If a future requirement needs more, it goes through MQTT or this spec gets a new version.

### 8.2 Framing

Length-prefixed frames, big-endian:

```
+----------------+-----------------------------+
| length (4 bytes) | JSON payload (length bytes) |
+----------------+-----------------------------+
```

- `length` is the payload size in bytes, max **16 MiB** per frame (data channel) / **64 KiB** (bootstrap).
- A bootstrap connection is a single request/response exchange, then close.
- The data channel is a single TLS session identified by a signed handshake message, carrying multiple frames (§8.3).
- This framing also applies to the **local IPC** channel between the client process and Lumy processes (port 10461), replacing the current single-`read()` MessagePack exchange. Lumy↔client messages use the same envelope with `src` = `"lumy"` (the `src` enum is `"client"`, `"server"`, or `"lumy"`) and the Lumy's traffic signed with the *client's* key (the Lumy runs under the client's trust domain; the IPC channel additionally requires the peer to be the local client process via socket peer-credential check on Linux/macOS and an access token on Windows).

### 8.3 Bulk data reference pattern

For payloads exceeding the MQTT limit (sensor output, packages):

1. The holding side stores the blob locally and includes in the MQTT message: `data.ref = { "channel": "data", "token": "<random>", "size": <bytes>, "sha256": "<hex>" }`.
2. The other side opens the data channel, presents a signed `data/fetch` message carrying the `token`, and streams the blob in frames.
3. Receiver verifies size + SHA-256 before accepting.
4. Tokens are single-use and expire after 5 minutes.

Direction determines which port is used (§2):
- **Server→client (package delivery):** the server opens a TLS connection to `client:10704` (`IPORT`) and pushes the blob. The client's inbound listener accepts the connection, validates the signed handshake, and streams the frames in.
- **Client→server (oversized results):** the client opens a TLS connection to `server:10465` (`LPORT`) and pushes the blob. The server's listener accepts, validates, and streams in.

In both cases the initiator presents the signed `data/fetch`/`data/push` handshake first; the receiver verifies before accepting any payload frames.

## 9. Reliability, Deduplication, Timeouts

### 9.1 Retries

- Transport-level: MQTT QoS 1 handles redelivery on the control channel.
- Application-level: the server retries unacknowledged `cmd` messages per its action policy (configurable). The client does not retry `resp`/`events` — redelivery is the broker's job via QoS 1; if the broker session is lost, the client re-publishes pending `resp`/`events` from its out-queue on reconnect (out-queue persists to disk, bounded size).

### 9.2 Deduplication

- Clients keep a ring buffer of the last **1,000** processed message `id`s (persistent across restarts is optional; in-memory is acceptable for v1).
- Servers deduplicate `resp` by `(uid, data.qid/aid, message id)`.
- A duplicate `id` with an identical signature is dropped silently; a duplicate `id` with a *different* signature is a security event (`ID_SPOOF_ATTEMPT`).

### 9.3 Timeouts

| Item | Default | Config key |
|---|---|---|
| Command deadline (query) | 120 s | `CMDTIMEOUT` **[NEW]** |
| Command deadline (deploy) | 3600 s | `DEPLTIMEOUT` **[NEW]** |

| Check-in interval | 5 min | `CHECKININT` (existing; delivered to clients via `setcheckinint`, §7.2) |
| Missing threshold | 90 days | `MISSINGAFTER` (existing) |

## 10. Protocol Versioning

- `v` = `MAJOR.MINOR`.
- A receiver MUST accept any message with the same MAJOR and MINOR ≥ its own, ignoring unknown fields.
- Unknown fields are ignored, not rejected (forward compatibility).
- Breaking changes bump MAJOR; both ends must support negotiation during a transition window. v1 has no negotiation mechanism — mixed-major environments are unsupported and logged.

## 12. Decisions & Open Items

### Resolved
1. **Signature algorithm** — Ed25519; Perl: `Crypt::Perl::Ed25519` v0.38 (installed, verified); Rust: `ed25519-dalek` (§3.4).
2. **MQTT broker** — Mosquitto, running as its own service (§1, §4.1, §4.3).
3. **Bootstrap trust anchor** — TLS-bound Ed25519 signing certificate (§7.1).
4. **MQTT version** — 3.1.1 (minimal install). No Message Expiry Interval; command TTL is enforced by the server-side timeout (§9.3) and client deduplication (§9.2) (§4.1).
5. **Data channel ports** — 10465 (server listener, client→server data + registration) and 10704 (client listener, server→client data) (§2, §8.3).
6. **Wire encoding** — JSON everywhere; MessagePack dropped (§5.4).
7. **Lumy IPC identity** — `src` enum extended with `"lumy"`; same envelope, signed with the client key (§8.2).
8. **Mosquitto auth + ACL mechanism** — built-in `password_file` (PBKDF2-SHA512, kept in sync with `CLIENTS.AUTH` and reloaded via `SIGHUP`) for login, and static `pattern` rules with `%u` substitution in an `acl_file` for access control. No C plugin or dynamic callback (§4.1, §4.3).

### Still open / to verify
- **`CHECKININT` vs. keepalive** — keepalive 60 s, check-in 5 min; confirm the Mosquitto session timeout is not shorter than the check-in interval plus margin (§4.1, §9.3).

## 13. Migration Notes (current code → v1)

| Current behavior | v1 change |
|---|---|
| Client sends MessagePack structs over raw TCP; broker expects a JSON+AES envelope | Single JSON envelope, signed, over MQTT (§5) |
| No framing on TCP; both sides `read_to_end`/read-until-close (deadlock) | Length-prefixed frames on direct channels only (§8.2); MQTT handles the rest |
| Broker never responds to the client | Every `cmd` gets a response; registration response defined (§7.1) |
| Client `heartbeat` action; broker handles `ping` | Single action: `checkin` (§6.1) |
| No client fingerprint sent; broker requires one | Client generates keypair at first run; fingerprint = SHA-256(pubkey) (§3.1) |
| AES-CBC + RSA key exchange per message | TLS for confidentiality; per-message signature for authenticity (§3) |
| Client inbound listener (10704) bound but never used | Now the server→client data channel for package delivery (§2, §8.3) |
| Lumy IPC: single 1024-byte read, MessagePack | Framed, signed, same envelope (§8.2) |
| `SKEY` compared in clear inside the message | `SKEY` used only in the bootstrap `register` request, inside a signed+TLS-protected message (§7.1) |
